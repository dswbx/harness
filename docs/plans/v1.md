## 2. Core API

**Core methods:**
- `Harness::execute(Command) -> CommandResult`
- `subscribe_session(session_id, from_seq, sink)`
- `subscribe_app(sink)` for installs and the session list

**Tauri exposes only three IPC commands:** `execute`, `subscribe` (`tauri::ipc::Channel<Event>` as the sink) and `unsubscribe`. A future daemon could reuse the same enums over WebSocket.

**Commands** are a tagged enum:
- App scope: sessions CRUD and archive, ListBranches, agents, registry, install, auth, frontends, MCP Library, permission rules, settings.
- Session scope: Prompt (returns at once; results arrive as events), Cancel, ResolvePermission{remember?}, SetMode, SetConfigOption, SendSlashCommand, ContinueWithSummary, StartSideThread (core only), Git{op}, FrontendState{read/write/list} confined to `frontend/`.

**Event envelope:** `{v, seq, session_id, thread_id?, ts_ms, kind}`.

**`EventKind`** is normalized and Harness-owned. It covers:
- Session and Thread lifecycle
- `AgentSessionStarted{boundary: initial|resumed|loaded|reseeded|agent_switched|continued_with_summary}`, `ThreadReadOnly`
- prompt turns
- message and thought chunks, tool calls
- `TaskListUpdated`, mode, config, commands, usage, compaction
- permission requested and resolved
- `FileEdited` (annotation only), terminal started, output and exited
- `WorkspaceChanged`, `FrontendToolOutput`, errors

**Replay.** The Session actor handles subscribe as one serialized step: replay the log from `from_seq` to the head, then switch to live, with no gaps or duplicates. Each View has a bounded queue; on overflow it gets `Lagged`, then resubscribes. Frontend code is a pure reducer `(state, Event) => state`, so replay and live share one code path.

**TS types.** A `gen-ts` step (specta-typescript) writes `packages/api/src/generated.ts`, plus a JSON Schema for `FrontendManifest`. CI checks for drift.

**Frontend Manifest:** `{id, version, name, frontend_tools[{name, description, input_schema}], needs}`. It is embedded in harness-tauri and registered at boot, so core knows a Frontend's tools even with no View open. A snapshot goes into `session.json` when the Session is created.

## 3. Storage

**Source of truth:** a JSONL Session Log per Session Directory (append-only, self-contained, schema `v` in the header). Writes are group-committed with fsync at prompt turn end and on permission events. A torn trailing line is truncated on open.

**App-level catalog:** `harness.db` (SQLite), rebuildable from the logs. It holds the session list, agent installs, permission rules, MCP Library and settings. Secrets go to the Keychain via `keyring`.

This choice is recorded as ADR 0010.

**On disk:** `~/Library/Application Support/<bundle-id>/`
```

worktrees/<session-id>/<repo>/
sessions/<session-id>/
  session.json  log.jsonl  acp-trace/  terminals/  snapshots/
  frontend/tools/<tool>/<seq>-<call-id>.json
```

M4 status (2026-10-26):
- **Implemented in `acp.rs`, `session.rs` and `summary.rs`:**
  - **Idle stop:** a watchdog runs per Agent process. It stops the process when no Turn is in flight, nothing is pending, no View is subscribed, and the idle timeout has passed. It logs `AgentProcessState{stopped}`.
  - **Generation guard:** a late exit can never clear its successor's connection.
  - **Crash:** the Turn ends as `error`, pending permissions are cancelled, and the next prompt respawns the Agent and resumes or loads its Agent Session.

  - **Side Threads (core only):** `StartSideThread{seed}`. Each Side Thread gets its own Agent Session on the Session's Agent process.
  - **Status** is derived from Turns in flight per Thread plus pending requests.
- **Verified:**
  - Fake-agent tests cover resume, load without a duplicate replay, read-only then continue, crash recovery, idle stop with and without an open View, and Side Threads.
  - Real Claude resumes across a Harness restart, checked with the smoke example plus `SMOKE_DATA` / `SMOKE_SESSION`.
- **Fix after manual testing:** killing the adapter under `npx` closes stdout without the process exiting. The connection now also ends on `incoming_closed`, and the next prompt respawns the Agent.

## 6. Risks

1. ACP crate Send-ness and maturity. Mitigation: isolate the connection in a per-process actor thread.
2. Adapters may skip client fs/terminal. ADR 0006 already covers this.
3. Plan Mode may surface in Agent-specific ways. Keep the Plan UI generic.
4. `session/load` replaying history could duplicate the log. Suppress replay correctly.
5. Agent auth flows (browser or terminal logins) may need a terminal-auth surface.
6. The Finder-launched app's environment may lack PATH, ssh-agent or credential helpers.
7. Localhost MCP exposure. Mitigated by the token, loopback binding and Origin check.
8. Log growth from chunks and terminal output. Mitigated by offloading terminal output and coalescing chunks later.

M7 status (2026-10-26):
- **Implemented:**
  - **Harness MCP (`mcp.rs`):** rmcp streamable HTTP on 127.0.0.1 with a random port, started lazily. An axum middleware maps a bearer token (one per Agent Session, revoked when the process exits) to Session and Thread, and answers 403 for any `Origin` header. The tool list is dynamic: Primitives `git_status`, `git_diff`, `list_branches`, `git_commit`, `git_push`, plus the Session's Frontend Tools.
  - **Permissions:** Harness MCP calls go through the Permission Policy with kinds `read`, `git_commit`, `git_push` and `frontend_tool`. Defaults: commit and frontend tools allow, push asks. An ask uses the normal permission flow with a Harness-side waiter. The Agent's own permission prompt for `mcp__harness__*` / `mcp.harness.*` is auto-allowed, so the user isn't asked twice.
  - **Frontend Tools:** inputs are validated with the `jsonschema` crate against the manifest's JSON Schema; errors go back to the Agent so it can retry. Valid calls are stored at `frontend/tools/<tool>/<id>.json` and logged as `FrontendToolOutput`. `FrontendRead`, `FrontendWrite` and `FrontendList` are confined to `frontend/`. Frontends author their schemas with jsonv-ts, and a build step writes them into `manifest.json`.
  - **Stdio shim:** `harness mcp-shim`, or the `harness-mcp-shim` bin in core, for Agents without `mcpCapabilities.http`.
  - **MCP Library (`library.rs`):** definitions live in `mcp.json`; secret env vars and headers go to the Keychain (`keyring`) and never to disk. Servers are picked per Session (`CreateSession.mcp_servers`) and passed on session new, resume and load. HTTP library servers are skipped, with a notice, for Agents without HTTP MCP.
- **Verified:**
  - Fake-agent tests (it is a real rmcp client): the tool list, git tools, commit allowed, push asked then denied, Frontend Tool validation and storage, the Frontend state commands and their confinement, the stdio shim, Library secrets reaching the Agent but never the file, and 401/403 on a missing token or an Origin.
  - Live: Codex (`mcp.harness.git_status`) and Claude (`mcp__harness__git_status`) both called the Harness MCP and answered correctly.
- **Not done:** Frontend Tool outputs are request/response only (no streaming), and the naive shim has no server-to-client streams.

## Backlog (after v1)

**Agent profiles: isolation and multiple accounts per Agent** (requested 2026-10-26)
- **Problem:** Agents keep their state in their own home folders, so Harness Sessions show up in the Agents' own apps. Codex stores its sessions in `~/.codex/sessions`, which the Codex desktop app lists. Claude Code stores them in `~/.claude/projects`, which appear in its resume list. The same home folder also pins one login per Agent.
- **Idea:** an Agent profile is an installed Agent plus its own home folder (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, …) under app data, its own login and env overrides. Profiles are named, e.g. "Codex (work)" and "Codex (personal)". The Composer picks a profile, and Sessions record the profile they started with.
- **Pieces:**
  - Editable env per installed Agent; there is no UI for it today, only Custom Agents take env.
  - A per-Agent "home variable" mapping, for the Agents whose variable is known.
  - "Isolate from the Agent's own app" as the default for new profiles.
  - Sign-in per profile, through the existing AuthRequired flow or the Agent's CLI login with the profile's env.
  - Optionally share the login with the default profile by linking `auth.json` (Codex). Claude on macOS keeps its login in the Keychain, so it needs a check per Agent.
- **Constraints:**
  - Resume needs the Agent to persist sessions, so isolation must move where they are stored, not turn persistence off.
  - A Session's profile cannot change later, because its Agent Session lives in that profile's home.
- **Workaround today:** a Custom Agent pointing at the installed adapter, with `CODEX_HOME=<folder>` (or `CLAUDE_CONFIG_DIR`) in its env.

**Clickable notifications** (requested 2026-10-26)
