# The `harness` command and the Folder Diff

Users want to start Harness work from a terminal: see the changes of the folder they are in, or start a Session there. The diff window needed a Session, the `harness` binary only knew `mcp-shim`, and no outside process could reach a running app.

**Decision:**

1. **`harness diff [dir]` opens a Folder Diff, `harness new [dir]` opens the Composer.** `dir` defaults to the current folder; the client resolves it against its cwd and makes it canonical. `diff` in a subfolder shows the whole repository, like `git status`. `new` only fills in the folder: the user picks the Agent and presses Create. No Session is created from outside. Exit codes: 0 ok, 1 usage error or app not running, 2 bad folder. With no command, `harness` opens the app or brings it to the front.
2. **A Folder Diff is the Session diff window with another data source.** One `DiffWindow` tree takes `source: {kind: "session"} | {kind: "folder"}`; both modes read through a `GitSource` (`gitDiff`, `gitLog`, `gitShowFile`), so a fix in the viewer applies to both. The core gets three additive Commands (`FolderGitDiff`, `FolderGitLog`, `FolderGitShowFile`) instead of a `GitDiff` that also takes a folder: the Session ones stay as they are, and the folder ones check the path (absolute, a directory, in a git repository). Defaults are shared with the Workspace: from where the changes start (the fork point from the default branch, else upstream, else HEAD; never a fetch) to the working tree. A Folder Diff has no Review Comments, which belong to a Session. It reloads with a Refresh button (both modes), not live.
3. **A Unix socket per data dir, not single-instance or a URL scheme.** The app listens on `<data dir>/cli.sock` (mode 0600). When that path is too long for a socket, it is `harness-<hash>.sock` in `$TMPDIR` if set, else in `~/Library/Caches/harness` (made 0700); the folder must be ours and not group/world-writable, else the app does not serve (never `/tmp`, which other users can write). At quit (`shut_down`) the app first removes its socket, only if the dev/inode still match the one it bound, and answers `quitting` to requests already accepted. A client reads `quitting` or a closed connection as "not running": a no-args launch starts the app, `diff`/`new` cold start and poll for a real `ok`. One JSON line per connection (`CliRequest`), the app answers `ok`. Dev and release builds share the bundle id, so `tauri-plugin-single-instance` would let a dev build catch the installed app's calls; the socket follows the data dir (`~/.harness`, `~/.harness-dev`, `HARNESS_HOME`). A `harness://` scheme can be opened by any web page, and a cold start through it would turn the terminal process into the app.
4. **Cold start: `open -a`.** With no socket, a binary inside a `.app` starts the app with `open -a <bundle>` and retries the socket for up to 20 s, so the terminal returns at once. A dev binary prints that the dev app is not running.
5. **The main window takes requests from a queue.** The app queues each request, brings the main window up (made again from the config if it was closed; a Dock click with no window does the same) and sends the poke `cli-request`. The Shell takes the queue (`cli_take`) once it listens and on each poke, so a request that comes during a cold start or a reload is not lost.
6. **One installed app per data dir.** On macOS, running the bundle's binary directly (the `harness` link with no command) would start a second app on the same data dir; LaunchServices (Finder, Dock, `open`) never does. So, before Tauri starts, a release build launched with no command first sends `Focus` to the socket; if a running app answers, the new process exits. A plain launch finds no socket and starts as before. Dev builds skip this check: several checkouts run `bun run dev` at once on the same `~/.harness-dev`; only the first one serves the socket. At startup the app does not take over a socket that answers (another app owns it) and removes one that does not (stale). Arguments that macOS passes to an app it launches (`-psn_…`, `-NS…`, `-Apple…`) start the app; an unknown command is a usage error.
7. **Install on PATH from the app menu** (release builds): "Install 'harness' Command in PATH…" links `/usr/local/bin/harness` to the bundle's binary, as root through the system password prompt when that folder is not writable (`osascript … with administrator privileges`). It refuses an app that runs translocated or from a disk image ("Move Harness to Applications first") and asks before it replaces a file it did not install. "Uninstall…" removes the link only when it points into a `Harness*.app`. The link survives updates: the updater replaces the bundle at the same path.

**Consequences:** the terminal can reach only the app of its own data dir. Two installed apps can no longer run on one data dir by launching the binary twice; dev builds still can. A folder's diff has no comments. `new` takes no prompt or Agent flags yet.
