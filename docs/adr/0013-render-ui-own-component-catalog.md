# render_ui: our own component catalog, not json-render or HTML

Agents show rich content (cards, tables, images, carousels) with one chat Frontend Tool, `render_ui`. Its input is a tree of nodes `{ type, props, children? }` from a fixed component catalog (`packages/frontend-chat/src/tools.ts`). We add components when a real case needs them.

**Why a catalog and not agent HTML (`render_html`):** the app renders each component, so theme, dark mode and sizes match the rest of the app. The core can validate the input and give the Agent exact errors. The log stores data, so better components also improve old Sessions, and a non-web Frontend could render the same tree. It costs fewer tokens, and no Agent script runs in the app. `render_html` (sandboxed iframe) stays a later option, only for content the catalog cannot show. Sandboxed JavaScript for values and actions: ADR 0016.

**Why not the json-render library:** its value is the catalog idea, which we keep, in its node shape. The library also brings state, actions, visibility rules and a streaming patch format (about 1.8 MB of zod-based code). We need none of these: a tool call arrives complete, and our schemas are jsonv-ts and JSON Schema in the core. Revisit if we need interactive components (buttons that act, forms).

**Schema shape:** one recursive node in `$defs`; `type` picks the props schema with `if`/`then`, so core errors name the wrong prop (`/root/children/0/props: "src" is a required property`). The tool description also lists the catalog as text, because some Agents drop parts of a JSON Schema.

**Images:** a Frontend marks a string `"format": "harness-image"`. The core (`frontend_files.rs`, ADR 0012 level 1) checks each local image before it asks for permission, copies it into `frontend/files/`, and records `src -> copy` in the event's `files`. The input stays as the Agent sent it, and the image still shows after the Workspace is gone. `https:` and `data:image/` URLs are not copied; the webview loads them directly.

**Growing the catalog (2026-10-30).** Every component's description goes into every Session's context, so a component must earn its place: an Agent gains something it cannot do with the existing ones. Prefer a prop or a variant to a new component (`icon`, `tooltip`, Choice `variant: list | buttons | select`, Input `multiline`, Table `sortable`/`filter`). Added on this basis: Diff (reuses the diff view), List (rich rows, optional checkboxes for todos), Checkbox, Switch, Accordion, Timeline, Chart (recharts, loaded on first use, colors from `--chart-*`). Then added: Mermaid and ANSI as Markdown fences (`mermaid, `ansi; so plain messages get them too; mermaid loads on first use with strict security), Grid, Log (ANSI), Trace, PullRequest. And FileLink (Diff file names too): opens a file of the Session's folder at a line in the user's editor (Settings > Editor: VS Code, Cursor, Windsurf, Zed, a custom URL template, or the system default; the core opens only paths inside the folder). The Session menu opens the whole folder the same way. Wait for a real need: Kanban, Dialog, Drawer, Popover. Each component needs an example (gallery and tests).

**Artifacts panel (2026-10-31).** The chat's right panel lists every render_ui item (latest content per id), Mermaid diagram and Markdown table of the Session, by Turn, filterable by kind and text; a row jumps to it in the chat or opens it in the panel with its source. It is derived from the chat Items (`artifacts.ts`), so it needs no core Event: render_ui is this Frontend's tool. PullRequest has three variants: summary (default, three lines), card and compact.

**Addendum (2026-11-02, generic primitives).** We explored UIs for multi-repo orchestration (a chain of boxes with labels between them, an inspector sidebar, a status table, a plan list with statuses) and chose not to add use-case components for them. Each would earn its place for one domain only. Instead the existing parts got generic props, and two small components were added:

- Stack: `align`, `justify`, `wrap`, and `fill` (default true: children in a row share the width, as before; false: each keeps its own width). Repeat takes the same layout props.
- Card: `variant` default, compact (less padding) or plain (no border or background: a section). A tone still colors the border and background.
- Table: a row is an array of cells (as before) or `{cells, tone}`; a cell is text (inline Markdown, as before) or `{text, tone?, mono?, icon?}`. Sorting and the filter use the cell text. Rows as objects keep the old array form valid and need no parallel `rowTones` array.
- KeyValue items take `tone` and `mono`. List items take `status` (done, running, waiting, blocked, failed): a status icon in place of `icon`, independent of `check`.
- Text: short plain text (size, weight, tone, mono, muted) for labels, numbers and arrows between other parts. Markdown stays the component for prose.
- Repeat: renders its children once per item of a state array (`items: {"$state": "/path"}`). The Agent patches the data and does not resend the tree.

Repeat's item scope follows json-render's repeat scope, so we can still adopt the library: `{"$item": "field"}` reads a field of the item (`""` the whole item), `{"$index": true}` the index, `{"$bindItem": "field"}` binds to `<path>/<index>/field` (written with `replace`, ADR 0015 addendum 2), a bare `${field}` in a `$template` reads the item first and then `/field`, and `visible` takes `{"$item": "field"}` or `{"$index": true}` with `eq`/`neq`/`not`. In actions, `statePath: {"$item": "field"}` is the item field's path (json-render's `resolveActionParam`) and `removeState` takes `index: {"$index": true}`. One difference: json-render puts `repeat: {statePath, key}` on any element; we use a Repeat component with `items` as a `$state` expression, because our nodes have no extra fields and a component shows up in the catalog and its schema. A Repeat maps one to one to a json-render element with `repeat`. Items not from state (a literal array) render but cannot be written. **Tooltips and Popover (2026-11-02).** `tooltip` now also on Text, KeyValue values, List items and Table cells (dotted underline on text, keyboard-focusable). Popover added: a click opens a floating box with the children. The trigger is a button from `label`, or else the first child, because json-render nodes have only `children` and no named slots. The content renders in a portal but in the same React tree, so state, bindings, actions and the Repeat scope work inside.
