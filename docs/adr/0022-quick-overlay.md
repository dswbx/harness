# Quick Overlay: a floating window that starts a Quick Session from any app

A Quick Session (ADR 0020) still needs the main window: switch to Harness, click the Quick group's +, type. Users want to ask something from where they are, like a launcher, and keep the answer on screen while they work in the other app.

**Decision:** a global shortcut (default ⌥Space, Settings > Quick overlay) opens the Quick Overlay: one floating, always-on-top window with a prompt box, just below the mouse or at the bottom center of the screen. The first message turns it into a small pinned chat, which can be minimized to one bar, merged into the main window, or closed.

**One window, made once.** Label `overlay`, URL `/?overlay=1`, created hidden on first use and never destroyed: close (and ⌘W) only hides it. It is one more Frontend window of the core, like the pop-out View windows: the Session syncs through the same `execute` / `subscribe` / `subscribe_app`. Signals between windows use Tauri events (`overlay-shown`, `overlay-shortcut` to the overlay, `select-session` to the main window).

**The webview owns the state, the host follows it.** `overlayMode.ts` is a pure reducer: `prompt` (a draft, only the prompt box), `chat` (pinned), `mini` (one bar, "New reply" when a Turn ends while mini), and `visible`. Each mode change calls `overlay_set_mode`. The shortcut shows a hidden overlay; on a visible one the webview decides: the prompt hides, a pinned chat switches between chat and mini (to start a new chat, close first). ⌘M and Esc minimize. 

**Placement.** "At the mouse" puts the card's top edge 12px below the mouse, centered on it, so the box does not cover what the user points at. Each mode change keeps the card's top center in place, so the chat grows down from the prompt box. "Bottom center" keeps the bottom center instead (the chat grows up). The host sends the anchor with `overlay-shown`; the page puts the prompt box at the top (or bottom) of its window to match. Placement is a pure `place()` in `overlay.rs` that keeps the window on the screen it opens on; with no room below the mouse it moves up.

**Resizable chat: a grip, not the window edge.** The user can resize the chat (min 380x300); its size is kept in the host for the app session, so expand after minimize and the next chat use it. The prompt and the mini bar have a fixed size. macOS gives a borderless window no resize edges (`resizable(true)` does nothing), and tao has no `drag_resize_window` there, so the chat card draws a small grip at its bottom-right corner (`nwse-resize` cursor). The page tracks the pointer (pointer capture, screen deltas from the size at the start) and sends `overlay_resize(width, height)` at most once per frame; the host keeps the window's top-left, enforces the minimum, clamps to the screen's work area and keeps the size. A titled window would give native edges, but not the look.

**The Quick Session is created when the overlay opens, not on send** (`CreateQuickSession` + `WarmUp`). The model list and the modes exist only once the Agent runs, so the prompt box and its option chips are the main window's, unchanged. Changing the Agent in the draft is `DiscardEmptySession` plus a new draft. The draft starts with the Agent last sent from the overlay, else `quickAgent`. The main sidebar hides Quick Sessions nobody wrote in yet, unless that window has one selected, so the draft never shows as an empty row. The core still decides what is empty and removes leftovers at startup (ADR 0020).

**Reuse, no look-alikes.** The overlay renders the chat Frontend's View with `variant: "overlay"`: no Stripes, Panels or header of its own, and before the first message only the `PromptBox`. A View prop `agentSwitch` turns the footer's model chip into a two-level Agent > model menu (other Agents' models are known only after they start, so picking one replaces the draft). The prompt box looks the same before and after the first message: the overlay always passes `agentSwitch` (then `locked`: other Agents show disabled, "Close to switch Agent") and the Mode chip stays its own chip; the overlay's footer never folds into the narrow box's one "Options" menu. The host draws the overlay's header (Quick chip, title, minimize, open in main window, close) and the mini bar; both are drag regions.

**macOS: a non-activating NSPanel** through `tauri-nspanel` (pinned git rev), in one module of `overlay.rs`: floating level, on every Space and over full-screen apps, does not hide when Harness is not active. Typing in it does not make Harness the active app; "Open in main window" does. This needs `macOSPrivateApi` (transparent window), which rules out the Mac App Store; Harness is not distributed there. Windows and Linux get the shortcut and an always-on-top window only.

**Look.** The window is transparent; the card is CSS (rounded corners, shadow, theme tokens), no vibrancy. The overlay window skips the opaque-background reveal of the other windows (`syncWindowBackground`, the page-load fallback).

**Shadow: CSS in a transparent margin, not the native window shadow.** The window is the card plus a 20px transparent margin on each side, and the card has a soft shadow (`shadow-overlay`) that fits in it, so no window edge cuts it. The native macOS shadow would need the card to fill the window, but the window must grow past the card for menus (below), and the native shadow of a transparent window follows its pixels only when recomputed (`invalidateShadow`), which would draw it around the menus or leave it stale. The margin takes clicks; they do nothing.

**Menu room: right and down only.** A page cannot draw outside its window, so menus (the Agent > model submenu, the Mode menu, the "/" and "#" lists) were cut at the window edge. While one is open (a `MutationObserver` on `body` sees a Radix menu, popover or list), the page calls `overlay_set_menu_room`: the host grows the window by 320px to the right and down, clamped to the screen's work area. The top-left never moves, so the card stays where it is with no page offset; the page only pins the card to its size from before (and unpins it once the window is back). When all menus close, the window goes back. One host call runs at a time, so a fast open and close cannot leave the window grown. The growth math is a pure `grow()` in `overlay.rs`. A first version grew the window on all four sides and padded the card by what was added; the move and the padding were two async steps, so the card jumped up-left while a menu was open. Because the window grows only down, in the prompt state (box at the top of its window), the menus open downward (`side="bottom"`; Radix flips or shifts one with no room, and the "/" and "#" lists open on the side with more room, which is up at the bottom of the screen). In the chat, menus open up inside the chat as in the main window; the room gives submenus space to the right. A click in the added area closes the menu, as outside a menu anywhere.
