# Quick Overlay: a floating window that starts a Quick Session from any app

A Quick Session (ADR 0020) still needs the main window: switch to Harness, click the Quick group's +, type. Users want to ask something from where they are, like a launcher, and keep the answer on screen while they work in the other app.

**Decision:** a global shortcut (default ⌥Space, Settings > Quick overlay) opens the Quick Overlay: one floating, always-on-top window with a prompt box, just below the mouse or at the bottom center of the screen. The first message turns it into a small pinned chat, which can be minimized to one bar, merged into the main window, or closed.

**One window, made once.** Label `overlay`, URL `/?overlay=1`, created hidden on first use and never destroyed: close (and ⌘W) only hides it. It is one more Frontend window of the core, like the pop-out View windows: the Session syncs through the same `execute` / `subscribe` / `subscribe_app`. Signals between windows use Tauri events (`overlay-shown`, `overlay-shortcut` to the overlay, `select-session` to the main window).

**The webview owns the state, the host follows it.** `overlayMode.ts` is a pure reducer: `prompt` (a draft, only the prompt box), `chat` (pinned), `mini` (one bar, "New reply" when a Turn ends while mini), and `visible`. Each mode change calls `overlay_set_mode`. The shortcut shows a hidden overlay; on a visible one the webview decides: the prompt hides, a pinned chat switches between chat and mini (to start a new chat, close first). ⌘M and Esc minimize. 

**Placement.** "At the mouse" puts the card's top edge 12px below the mouse, centered on it, so the box does not cover what the user points at. Each mode change keeps the card's top center in place, so the chat grows down from the prompt box. "Bottom center" keeps the bottom center instead (the chat grows up). The host sends the anchor with `overlay-shown`; the page puts the prompt box at the top (or bottom) of its window to match. Placement is a pure `place()` in `overlay.rs` that keeps the window on the screen it opens on; with no room below the mouse it moves up.

**Resizable chat: a grip, not the window edge.** The user can resize the chat (min 380x300); its size is kept in the host for the app session, so expand after minimize and the next chat use it. The prompt and the mini bar have a fixed size. macOS gives a borderless window no resize edges (`resizable(true)` does nothing), and tao has no `drag_resize_window` there, so the chat card draws a small grip at its bottom-right corner (`nwse-resize` cursor). The page tracks the pointer (pointer capture, screen deltas from the size at the start) and sends `overlay_resize(width, height)` at most once per frame; the host keeps the window's top-left, enforces the minimum, clamps to the screen's work area and keeps the size. A titled window would give native edges, but not the look.

**The Quick Session is created when the overlay opens, not on send** (`CreateQuickSession` + `WarmUp`). The model list and the modes exist only once the Agent runs, so the prompt box and its option chips are the main window's, unchanged. Changing the Agent in the draft is `DiscardEmptySession` plus a new draft. The draft starts with the Agent last sent from the overlay, else `quickAgent`. The main sidebar hides Quick Sessions nobody wrote in yet, unless that window has one selected, so the draft never shows as an empty row. The core still decides what is empty and removes leftovers at startup (ADR 0020).

**Reuse, no look-alikes.** The overlay renders the chat Frontend's View with `variant: "overlay"`: no header of its own, only side panels (Phase 2, below), and before the first message only the `PromptBox`. A View prop `agentSwitch` turns the footer's model chip into a two-level Agent > model menu (other Agents' models are known only after they start, so picking one replaces the draft). The prompt box looks the same before and after the first message: the overlay always passes `agentSwitch` (then `locked`: other Agents show disabled, "Close to switch Agent") and the Mode chip stays its own chip; the overlay's footer never folds into the narrow box's one "Options" menu. The host draws the overlay's header (Quick chip, title, minimize, open in main window, close) and the mini bar; both are drag regions.

**macOS: a non-activating NSPanel** through `tauri-nspanel` (pinned git rev), in one module of `overlay.rs`: floating level, on every Space and over full-screen apps, does not hide when Harness is not active. Typing in it does not make Harness the active app; "Open in main window" does. This needs `macOSPrivateApi` (transparent window), which rules out the Mac App Store; Harness is not distributed there. Windows and Linux get the shortcut and an always-on-top window only.

**Look.** The window is transparent; the card is CSS (rounded corners, shadow, theme tokens), no vibrancy. The overlay window skips the opaque-background reveal of the other windows (`syncWindowBackground`, the page-load fallback).

**Shadow: CSS in a transparent margin, not the native window shadow.** The window is the card plus a 20px transparent margin on each side, and the card has a soft shadow (`shadow-overlay`) that fits in it, so no window edge cuts it. The native macOS shadow would need the card to fill the window, but the window must grow past the card for menus (below), and the native shadow of a transparent window follows its pixels only when recomputed (`invalidateShadow`), which would draw it around the menus or leave it stale. The margin takes clicks; they do nothing.

**Menu room: right and down only.** A page cannot draw outside its window, so menus (the Agent > model submenu, the Mode menu, the "/" and "#" lists) were cut at the window edge. While one is open (a `MutationObserver` on `body` sees a Radix menu, popover or list), the page calls `overlay_set_menu_room`: the host grows the window by 320px to the right and down, clamped to the screen's work area. The top-left never moves, so the card stays where it is with no page offset; the page only pins the card to its size from before (and unpins it once the window is back). When all menus close, the window goes back. One host call runs at a time, so a fast open and close cannot leave the window grown. The growth math is a pure `grow()` in `overlay.rs`. A first version grew the window on all four sides and padded the card by what was added; the move and the padding were two async steps, so the card jumped up-left while a menu was open. Because the window grows only down, in the prompt state (box at the top of its window), the menus open downward (`side="bottom"`; Radix flips or shifts one with no room, and the "/" and "#" lists open on the side with more room, which is up at the bottom of the screen). In the chat, menus open up inside the chat as in the main window; the room gives submenus space to the right. A click in the added area closes the menu, as outside a menu anywhere.

**Phase 2: `render_ui` Panels beside the chat, in the same window.** No extra OS windows: the dock needs one shared parent (ADR 0019). The overlay View renders the main window's `DockLayout`, `Stripe` and `PanelHeader` (title, menu with Move to, hide); nothing in the panel chrome is overlay-specific. Differences, all as options of the shared parts:

- Only `render_ui` panels (left or right placed items), no built-in ones. An item opens in its ADR 0019 default zone (right items right top, left items left top) when the Agent adds or changes it.
- Only the side zones (`OVERLAY_ZONES`: left top, left bottom, right top, right bottom). `overlayProfile` moves panels of the bottom zones to right bottom, Move to and the drop targets offer only the four. The layout is kept in memory, not in the Session's stored layout, so the main window's layout of the Session does not change.
- The stripes are tabs attached to the chat card's left and right edges (only on a side that has icons); the card's border is the line between them. Panels are floating cards (`DockLayout` `floating`: rounded, shadow, 8px gap).
- The host draws the card around the View's chat column (`chatFrame` View prop: header, border, resize grip), so the panels and stripes sit outside it.

**The window grows by the panels; the card stays put.** The View reports the room it wants left and right of the card (`onPanelWidth`: open side columns at their sizes, `sideWidths` in `panelLayout.ts`, plus 40px per stripe; 0 before the first message). The page sends it with `overlay_set_panels(left, right)`; the host keeps it and, in the chat, sets the window to the card frame plus that much on each side (`beside`, `card_of`, `widen` in `overlay.rs`): a left panel grows the window to the left, a right panel to the right, so the card does not move. With no room on one side the whole window moves to stay on the screen (the card moves with it); a window wider than the screen keeps its width (so `card_of` stays exact) and starts at the screen's left edge. Mode changes place the card, then add the panels; the mini bar and the prompt have none, so panels hide while mini and come back on expand.

**The chat card has a fixed width; it never follows the window.** A first version sized the chat from the measured window width. The window resize (a resize, then a move: two native steps) and the page's re-layout came a frame apart, so the card moved by a few px and the chat got another width for a frame: its text re-flowed and the message list's scroll jumped. Now the page gives the card a fixed width (the host's chat size, `overlay_chat_width`; only the resize grip changes it, `overlay_resize` returns the new width) and lays the row out as `room left + card + room right`, where room is what the host has granted (`overlayGeometry` in `panelLayout.ts`, `DockLayout` `width`). The order is: a side that wants more room grows the window first, and its panels (and stripe) draw only when the room is there; a side that wants less stops drawing at once, then the window shrinks. The row keeps to the window edge that does not move: the right one while only the left side changes (`rowEdge`), else the left one (also while a menu has room or the grip is dragged). On macOS the host moves and resizes the window in one call (`setFrame:display:animate:`, `panel::set_frame`); elsewhere it is a resize, then a move. One host call at a time, as for the menu room.

**Resize grip and menu room with panels.** The grip resizes the card: the page sends the card's size (plus the shadow margin), the host keeps the card's top-left, puts the panels beside it at their widths and returns the card width; the page then sets its card to it (window first, then card); `chat_size` is the card size alone. The menu room is unchanged (right and down from the whole window); a panel change while it is open only changes the frame to go back to. Dragging a panel's resize line changes its width; the card stays and the window grows on the panel's side, so the line does not follow the pointer exactly.

**First open without a black flash.** The overlay window is created hidden at startup (with a transparent background) so its page loads early. The page calls `overlay_ready` after its first paint (two animation frames). A shortcut before that only records `pending_show`; `overlay_ready` then shows the window. The window is never hidden-and-reloaded, so later opens are unchanged.

**Phase 3: Window Context, no screenshots.** The user pastes system screenshots (⌘V works), so the overlay takes none. While the overlay is open, the host follows what the user is looking at in other apps (`context.rs`) in three levels. Harness never asks for a permission itself:

- Level 0, no permission: the frontmost app's name, bundle id and pid (`NSWorkspace.frontmostApplication`). The NSPanel never activates Harness. Harness itself frontmost (the user clicked a Harness window): the last context stays; right after a show it is cleared.
- Level 1, Accessibility, only if `AXIsProcessTrusted()` is already true (never the prompting variant): the AX C API gives the focused window's title (`AXTitle`), its file (`AXDocument`, a file URL) and the focused element's selected text (`AXSelectedText`, at most 2000 characters). `AXManualAccessibility` is set on the app first, so Electron apps (Slack, VS Code, Cursor) build their tree; other apps ignore it. AX calls time out after 0.5s.
- Level 2, Automation: an AppleScript per known app (`Adapter`, matched by bundle id), run with `osascript` on its own thread, killed after 60s, so the user can answer macOS's prompt (asked once per target app the first time; the only prompt, and only known apps get a script). At most one script runs per app; a result for an older context is dropped and the current one runs next. Safari: URL and name of the current tab. Chrome, Arc, Brave, Edge, Chromium, Vivaldi: URL and title of the active tab. Finder: the insertion location's POSIX path and up to 20 selected items. iTerm2: `session.path` of the current session. Not Firefox (no AppleScript for tabs), not Terminal (no reliable folder). Error -1743 (not allowed) marks `automation` as missing. Script errors are logged at `warn` with the bundle id and osascript's error output. Debug builds log `AXIsProcessTrusted` at startup.

**Flow.** While the overlay shows the prompt or the chat (not mini, not hidden), a thread polls levels 0 and 1 every second (`overlay.rs`). A new app, window or document (`context::change`) starts level 2 and is sent as `overlay-context` when the script is done, or after 1.5s without it; the script's late result (e.g. after the Automation prompt) is sent again and the chip updates. A changed selection alone is sent without a script. `overlay_context` returns the last one for a page that mounts late. The prompt box shows it as a chip in the prompt and in the chat (`PromptContext` View prop: label, tooltip with all details, remove, attachment). The chip has one link: "Allow browser access" (or "Allow access to Finder") opens System Settings > Privacy & Security > Automation when `automation` is missing, else "Allow more context" opens Accessibility (`overlay_open_privacy_settings`, opener plugin). The page formats the chip and the attachment (`windowContext.ts`).

**Privacy: only what the chip shows is sent, and only while the chip is shown.** Each message sends the current context as a pasted Markdown attachment (`AttachmentInput::Data`, `text/markdown`, named e.g. `Context - Google Chrome · github.com.md`): app, window, page, URL, file, folder, selected files, selected text (quoted, at most 2000 characters). The message text stays exactly as typed; the bubble shows the attachment as a file chip. The core needs no change: it stores pasted non-image bytes in the Session's `attachments/` and sends them as an embedded text resource (or a resource link when the Agent has no embedded context). Removing the chip drops that context (same app, window, document and URL); another one shows the chip again. Settings > Quick overlay > "Include window context" (`OverlaySettings.window_context`, default on) turns it off: no poll, no chip.

**Packaging.** `crates/harness-tauri/Info.plist` (merged by Tauri, also embedded in dev builds) has `NSAppleEventsUsageDescription`; `Entitlements.plist` has `com.apple.security.automation.apple-events` for the hardened runtime (`bundle.macOS.entitlements`). In `bun run dev` macOS gives the Accessibility and Automation permissions to the terminal app that runs it, not to Harness.
