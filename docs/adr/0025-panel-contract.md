# Panel contract: one definition per panel, one registry in the shell

The chat's panels (ADR 0019) were wired in the View by hand: a panel's label, icon, shortcut, availability, badge and model each lived in `View.tsx`, and opening one at something (a file at a line, a diff scope, a plan) went through a pair of props per panel plus a focus nonce. Adding a panel touched about eight places. The layout stored the Side Thread tabs, and the reducer imported from four features.

**One definition per panel, in its feature folder.** `features/<f>/panel.tsx` builds the panel with `definePanel` (`panels/contract.ts`): id, label, icon, placement hint, optional shortcut, `useModel` (a hook that runs every render, open or not: derived data, state that must survive hiding), `status` (`absent`, `icon` or `ready`, plus badge, dot, tip), the `Body`, and how it mounts (`whenOpen`, `afterFirstOpen`, `whileReady`). The value is also the panel's typed handle: `ctx.open(filesPanel, { path, start })` opens it at a target the panel declares, and the panel applies each target once with `usePanelTarget`. A panel that a View cannot show (Files in the Quick Overlay) names a `fallback` for a target (it opens its window). A body gets `{ model, ctx, self }`; `PanelCtx` and `PanelSelf` keep their identity until an input changes.

**One registry, in the shell.** `shell/panels.ts` lists the panels; its order is the default order within a zone. `shell/usePanelHost.ts` builds each panel's context and self, runs the models and reads the statuses; the dock reads only that. The registry is a plain list that the shell imports, not panels that register themselves on import: with self-registration, order and presence would depend on import order and tree-shaking, tests would share global state, and the Terminal's lazy chunk would load early.

**Panel families for render_ui panels.** The Agent creates `render_ui` panels at runtime, so they cannot be registered. A family (`PanelFamily`, `features/renderUi/slotPanels.tsx`, prefix `slot`) lists its instances from one model; each instance is a panel with the id `<prefix>:<key>`. Ids are `slot:<id>`, as stored layouts already had them.

**Side Thread tabs belong to the Side chats panel.** They are not panels and not part of the layout: `features/sideChats/threadTabs.ts` holds them (open threads, the active one, drafts) under their own key, `harness.chat.sideThreads.<sessionId>`. "Reset layout" resets placement only.

**The layout is versioned.** Same key, `harness.chat.layout.<sessionId>`. v0 is the oldest key (`harness.chat.panel.<sessionId>`), migrated on load. v1 has no version field. v2 (written now) is `{ v: 2, zones, open, sizes }`. Panel ids are plain strings and are persisted: they never change (a test pins them). A stored id that no panel or family instance names keeps its place and does not render, so a downgrade or a removed render_ui panel loses nothing. Every panel is restored as it was, the Terminal too (this corrects ADR 0019). While the Side chats tabs have no key of their own, the `threads`/`thread` fields of the value being replaced travel along in v2 untouched, so no tab is lost whatever the order of the two writes. The dock's code is `shell/dock/` (`model`, `geometry`, `overlay`, `persist`).

**Layering.** `features/`, `state/`, `panels/` and `lib/` never import `shell/`; `state/`, `panels/` and `lib/` do not import `features/` (`scripts/boundaries.ts`, checked by `bun run typecheck`; the few edges of `state/` into `features/` that remain are listed in `scripts/check-boundaries.ts` and that list only shrinks). The shell is the chat's arrangement: the dock, the stripes, the Quick Overlay profile, the chat column and the jump helpers. Everything else is reusable: a second Frontend (a canvas, say) writes only where boxes go, how they persist and what "open" means, and reuses every panel definition, model and body, the families, the targets, the reducer and the Side Thread tabs. That holds while it lives in `frontend-chat` or until a shared package is extracted.

**Rejected.** Context only, without a registry: it fixes prop drilling but leaves the eight touch points in the View. Self-registering panels: see above.
